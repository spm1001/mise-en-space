## For Claudes to come

**Watch it fail *narrowly*.** This repo already holds that a passing test proves nothing until you have watched it fail. The sharpening: check that the red is a *single test you predicted in advance*. Tonight, reverting the Gmail parser to its old second-segment capture reddened exactly one test, and separately disabling the Chat guard reddened exactly one different test. That narrowness is the actual evidence — it proves each test tests the thing it names, and that the others are not quietly riding on the same production line. A control that reddens half the file tells you the suite is wired to the code and nothing about which assertion holds which line. And if *more* goes red than you expected, you have learnt something about your tests rather than about your fix. Cheap to do: revert one line, predict the failure set out loud, run, compare.

**When the task is deciding what is no longer needed, the work queue is the oracle — not the artefact.** Compacting a 14,828-word document is a deletion problem, and every criterion for deletion is really a claim about what future work will need. The instinct is to read the document harder. The move that actually worked was reading all 34 open bon items first, which cost 20k tokens and revealed that the compaction plan — careful, measured, written five days earlier by a Claude who had read the whole file — would have deleted the briefing for four live roadmap items, because the evidence those items rest on was probed three days after the plan was written. **A plan is a borrowed frame even when you wrote it, and a plan about deletion is the most dangerous kind, because its failures are invisible by construction: nothing goes red when you delete the wrong thing.** Generalises past documents to any pruning task — dead code, unused config, stale fixtures, backlog triage. Read the queue before you read the thing.
