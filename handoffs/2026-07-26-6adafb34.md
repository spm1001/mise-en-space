### Reflection

The useful move was refusing to edit the file I was pointed at until I knew what wrote it. Four layers exist — `mise-en-space` (source) → `batterie/plugins/mise` (vendored) → `plugins/cache/.../mise/<v>` (installed) → `rules/mise.md` (regenerated hourly, effectively) — and only the first is hand-editable. `~/repos/spm1001/batterie-home` reads like source and is a generated artefact; its tube checkout is stale from 7 July and still carries the pre-betiko `ln -sf` hook, which is what let me prove tube's orphan shard couldn't have come from a local install.

Making the routing rule **static** rather than derived per flavour was the design call I'd defend hardest. The hook already had identity plumbing, so deriving the text was tempting — but there are only ever two flavours, so derivation buys nothing and costs a substitution rule the transform has to keep in step forever. Identical bytes can't drift. The identity fields stay because the *no-token warning* genuinely needs them: that message has to say which flavour is unauthed and which sibling is fine.

Two verification notes worth carrying. First, `grep -c 'You are \*\*'` on the fixed hook returns **1** — from my own comment quoting the old wording to explain why it went. Grepping source proves a string is present, not that it's emitted; I had to run the hook against a fake `$HOME` and assert on the output. Second, I deliberately left the CSO description score at 65/D: `method_preview` matches literally on `\d+-step`, `\d+-phase`, `framework`, `workflow`, and this is a reference-and-offer skill, not a numbered process. Scoring those points would have meant writing a lie into the description. Sameer folded both the mechanism trap and the grep-the-source trap into `context/traps.md` and `context/verification.md` mid-session.

## For Claudes to come

**Converting always-on context into an on-demand skill is not a loss of discoverability, because a skill's description is itself always-on.** You trade twenty lines of standing context for one line in the picker and keep the unprompted discovery that made always-on attractive in the first place. This matters wherever a shard carries guidance for an audience the session isn't serving — here, planetmodha family install instructions loading during ITV work. The test for whether it's safe to move: does the reader need to *recognise* they need it (keep it always-on — you can't lazy-load a trap you don't know you're about to hit, which is why `traps.md` stays hot), or will they *ask* for it (a skill is enough)? Install guidance is asked for; hazards are not.

Two corollaries, both bought this session. **When you relocate something a doc explicitly says "don't remove", update that doc in the same commit** — otherwise the next Claude reads the instruction, believes it, and reverts you. And **ship a ratchet with the move**, so the reversion fails the build loudly instead of quietly reappearing in standing context where nobody reads it.

Finally, on layered build pipelines generally: when a file exists at four layers, the question "where do I edit this?" has exactly one right answer and three that look right. Establish the writer before the edit. The cheapest discriminator is almost always a timestamp — a file whose mtime equals the current session's start time is generated, whatever it looks like in `ls`.
