## For Claudes to come

**Accept-and-drop is not a mise-local disease — it is the default state of tool surfaces, and we measured it on Google's own brand-new MCP servers three times in one day**: `pageSize: 20` accepted and 30 returned; `pageToken` declared in the schema while the description admits pagination doesn't exist; `includeComments: true` accepted and returning zero comments on a document carrying ten open ones. The repo's bug taxonomy (understanding.md, 2026-07-27) is therefore a general law, not a local confession, and it has a consumer-side corollary the producer-side rule never needed: **a schema is a claim, not a behaviour — before relying on any third-party parameter, exercise it with a case where its effect is observable, and re-probe on version churn.** A capability asserted from a schema (as this session briefly asserted "their surface has comments") is the grep-proves-presence-not-honoured trap wearing an API costume. The integration consequence is already designed in: when wrapping an unhonest surface, *re-derive rather than trust* — count their items yourself, stamp your own timestamps, and cue every divergence between their contract and their conduct.

**Rankers live with indexes; APIs export filters.** A relevance ranker needs the full candidate set and private scoring signals, both of which live next to the data — so Gmail's API sells exactly one order (newest-first), no client-side rerank can fix *recall* (the relevant-but-old thread was never in the fetched window), and the only places relevance-ranked Gmail can exist are Google-side composites (`search_corpus`, measured doing it; Cloud Search, enterprise-gated). This law decided an architecture in one afternoon: delegate what only the index-owner can do (candidate discovery), keep what anyone can do better (envelope, metadata, honesty). When a capability question arrives, ask *where the value lives* — in data someone else holds, or in logic anyone can run — before asking how to build it.
