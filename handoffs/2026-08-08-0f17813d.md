## For Claudes to come

**A probe that only confirms is a probe half-read — tonight's three each changed a design.** The mechanism worth internalising: Google's write surfaces accept-and-enrich (write "@" + chipRuns, read back the file's live title) or accept-and-ignore (Drive revision names, keepForever), and nothing in the 200 distinguishes them — so the read-back IS the design input, not a verification formality. The chip probe is the cleanest exemplar: the enrichment (title replaces value) was the fact that flipped the design from auto-chip to opt-in.

**The two-pass rich-write pattern for Sheets generalises**: anything wanting typed values AND rich content writes the plain grid through values.update USER_ENTERED (numbers, dates, formulas parse), then overlays rich elements through one batchUpdate whose fields mask touches ONLY the rich fields — the value from pass one stands. Trying to do both in one updateCells pass forces you to re-implement Google's type inference by hand.

**One-letter API asymmetries produce false double-zeros**: Sheets spells the hyperlink key `link.uri`, Docs spells it `link.url`. A probe walker keyed on the wrong one reports links absent while staring at them — and a double-zero (no chips AND no links) from a fresh probe should always be read as "instrument first, subject second", because two simultaneous genuine negatives are rarer than one wrong field name.

**Ground truth has instruments too**: hasati's false-positive corpus was "pages where pdfplumber found no tables" — but pdfplumber's table finder is ruling-line-based and blind to borderless grids, so every "false positive" the new signal fired on turned out to be a real table. Before scoring a detector against a ground-truth column, ask what the ground-truth instrument itself cannot see; eyeball the disagreements before believing either side.
