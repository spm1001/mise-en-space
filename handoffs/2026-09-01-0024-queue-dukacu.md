## For the next Claude

### Done — mise-dukacu (CLOSED)

Google's 2026-08-31 Developer Preview made Slides and Sheets comment anchors legible for the first time. Until last night, mise could tell you *what* a comment on a deck said but never *where* it was; comments came out in whatever order the Drive API returned them. Now a deck's comments render in deck order, each under a `↳ slide 3 (Roadmap)` line, and a workbook's in tab-and-cell order under `↳ Sheet1!B12`. This is the treatment Docs have had since mise-jimive, finally reaching the other two surfaces. Commit `86d3752`.

**Which plane the locators come from, and why it matters if you ever revisit it.** There were two candidates. Drive's `comments.list` returns an `anchor` string per thread, and for Slides page anchors that string is legible JSON, so it looked free. It was rejected: on Sheets the same string carries an opaque range uid — the real cell range exists *only* in the new preview read — and the Slides shape-anchor spelling that hand-made UI comments produce was never measured on the Drive plane at all. Using one plane for both surfaces means one degradation path to reason about instead of two. That is `adapters/comment_anchors.py`, two thin GETs carrying `commentsViewMode=COMMENTS_VIEW_MODE_INCLUDED`; the pure resolution lives in `extractors/comment_anchors.py`.

**The join is outer and one-directional, and that is load-bearing.** The Drive comments plane decides which comments exist and render. The anchor map can only ever *add* a locator to one of them. There is no code path that removes a comment from the deposit. Sameer's falsifier on the card was verbatim *"we miss some gnarly edge cases and lose comments to the void"*, so the load-bearing test in the suite is not that a locator is pretty — it is `test_no_comment_is_lost_whatever_the_map_says`, which throws four unplaceable comments at the renderer (an orphan, an unanchored thread, one the preview never mentioned, one with an empty id) and asserts every single body still appears. **If you are ever tempted to make that join an inner join for tidiness, don't** — the comment in the module says so too.

**Degradation is a legal requirement here, not resilience engineering.** The DPP program terms bar shipping pre-GA features to customers (term iv), mise is publicly distributed, and enrollment rides a registered account plus Cloud project — so another ITV colleague's token through the same client may simply be refused. Every failure of the preview read therefore produces exactly the old flat render plus a `cues.warnings` line naming the surface, the HTTP status, and enrollment where the status implies it. Verified against a **real Google 400**, not a stub: force it by setting `adapters.comment_anchors._COMMENTS_VIEW_MODE` to an invalid enum value in-process and running a fetch. The comment-id sets in the degraded deposits were identical to the enrolled ones on both surfaces.

### The essayeur round — it found a comment-losing bug that predates this work

A cold-context essayeur was briefed narrowly: make a comment vanish, or make a locator lie. Verdict **CONFIRMED-WITH-CAVEATS**. The locator machinery survived everything (duplicate ids, empty ids, shared anchorIds, an anchorId under two slides, missing container keys both ways, partial and garbage GridRanges, columns past ZZ, RTL and punctuated tab titles). The caveats were three real defects, all fixed in the same commit:

1. **A busy file could lose every open comment, silently.** `_enrich_with_comments` asks for 100 threads, and the `include_resolved=False` filter ran *after* that cap. So a file whose first hundred threads in API order happened to be resolved returned **zero** open comments — no `comments.md` written at all, `open_comment_count` 0, no warning, indistinguishable from a file nobody has ever commented on. This predates the locator work by a long way and is exactly the failure Sameer named. The filter now runs inside the pagination loop, so the cap counts what is kept.
2. **A capped read stated a total it could not know.** `## Comments on "X" (100 total)` was printed whether or not more existed. A surviving `nextPageToken` now sets `FileCommentsData.truncated` and the header reads `(100+ — capped, this file has more)` with a warning beside it. This copies the `SearchResults.truncated` contract from mise-werevi, for the same reason: `len(comments) == max_results` can never distinguish an exactly-full read from a truncated one, so the token is the only evidence.
3. **A time-of-check race could make a locator lie.** `fetch_slides` reads the deck, then spends up to ~20 seconds fetching thumbnails, then reads the anchors. A slide inserted in that window is in the second read and not the first, and the old code fell back to labelling it by its position in the anchor payload — which names a *different* slide from the one the deposit numbers that way. A locator that lies is worse than one that is missing, because the reader has no cue to doubt it. It now says "on a slide that is not in this deposit".

Two smaller ones, also fixed: `extract_comments_content(max_length=…)` breaking at a comment boundary left no truncation marker and no warning (dormant — no live fetch path passes `max_length`), and a 200 response carrying no `slides`/`sheets` key degraded with no cue at all.

**Every new guard was mutation-controlled to red before its green was believed** — inner-joining the locator map, swallowing the refusal reason, filtering resolved after the cap, hardwiring `truncated` False (with its exactly-100 positive control staying green), and trusting the payload index. Five mutations, all caught, sources restored and diffed.

## For Claudes to come

**A cap that discloses beats a cap that counts wrong, and the difference is one boolean.** mise had already learned this once — Drive search carries a `truncated` flag set by a surviving `nextPageToken`, with a positive-control test proving it can read False. The comments read, in the same file, thirty lines apart, had no such flag and printed a confident total it could not know. Nobody had connected them, because the search lesson was written up as being about *search*. When you fix a truncation-honesty bug, grep the file for every other paginated read before you leave.

**The ordering of a filter against a cap is a silent correctness bug, not a style question.** `fetch_file_comments` filtered resolved comments *after* capping at 100, so a hundred resolved threads could starve every open one and the deposit would say "no comments" about a file full of live discussion. Nothing errored, no test failed, and the code read perfectly naturally — the filter was at the bottom where filters go. The general form: **when a cap and a filter act on the same sequence, ask what the cap is counting.** If it counts rows you are about to throw away, the answer the caller gets is not the answer they asked for.

**A locator that lies is worse than a locator that is missing.** Both of the deliberate design choices here follow from that. A comment whose anchor resolves to nothing gets `⚠ the anchored content no longer exists` rather than quietly losing its `↳` line, because "no location" and "the thing this was attached to is gone" are different facts a reader triaging comments needs. And a slide the anchor map knows but the deposit does not gets told as such, rather than borrowing the number of whatever slide happens to sit in that position — the reader is holding the deposit, so a slide number is a claim about *their* copy, not about Google's.
